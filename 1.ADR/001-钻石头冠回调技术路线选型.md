# ADR-001：钻石头冠回调的技术路线选型

- 状态：**Accepted**（2026-08-27 用户拍板：**采用 RitsuLib 依赖路线**；此前推荐的零依赖方案转入备选区）
- 日期：2026-08-27
- 关联调研：3.DOCS/001-E-钻石头冠版本差异取证.md、3.DOCS/002-R-BaseLib与RitsuLib调研.md、3.DOCS/003-T-STS2-Modding机制事实速查.md

## 背景

- 效果差异本质：107 的实现依赖一个**专属 PowerModel 子类** `DiamondDiademPower`，该类在 111 已被删除；111 版遗物本体逻辑整体换血。所以本 mod 与既往回调系 mod（同步/王座/飞拳）不同：不只是改方法体，还要在“宿主没有这个类”的前提下重建一个可施加、可显示、有图标、有文本、参与减伤计算链的 buff 实体。
- 跨版本铁证限制：`AbstractModel.ModifyDamageMultiplicative` 在 107=5 参 / 111=6 参，单一 C# override 不能横跨两版；四个战斗生命周期虚方法签名则两版一致。

## 决策（Accepted 版）

D0. **引入 STS2-RitsuLib 作为框架依赖**（用户决策）：manifest `dependencies=[{"id":"STS2-RitsuLib","min_version":"0.5.15"}]`，NuGet `STS2.RitsuLib`。
- 使用其价值点：带诊断的 `ModPatcher`（`IPatchMethod` 强类型补丁、稳定 PatchId、ApplyRequiredPatcher 失败自动禁用）；
- `PatchTarget.OptionalMethod`（ignoreIfMissing=true）天然承接“该成员仅存在于特定版本”的可选兼容目标场景；
- `HarmonyAsyncTaskBridge.After(...)` 处理 async 钩子的任务链替换；
- 日志走 `RitsuLibFramework.CreateLogger`；
- **不使用** variant-pack 双变体机制（它是 RitsuLib 自身的分发方式，业务 mod 无现成复用面；本 mod 的版本差异区域已被条件挂载覆盖，见 D3）。
D1. 单 DLL 双版本，不做条件编译、不做变体双包；csproj 引用游戏当前的 sts2.dll，**编码纪律=只引用两版共有成员**（杂耍计数 ADR-003 原则），版本特有成员一律经 Optional/dynamic 目标进入。
D2. mod 程序集内新建最小自定义 power：`RevertDiamondDiademPower : PowerModel` 只 override 两版稳定的 abstract 成员 Type/StackType；靠官方原生发现链 `ModelDb.AllAbstractModelSubtypes ⊃ GetSubtypesInMods` 收录；文本走自建键 `REVERT_DIAMOND_DIADEM_POWER.*`（slug 随类名自动推导）。
D3. **宿主形态判定前置到 ModEntry**（行为级判据，非版本号）：`AccessTools.DeclaredMethod(typeof(DiamondDiadem),"AfterSideTurnStart") != null` 即“新效果版”；同时要求 `AccessTools.TypeByName("...Powers.DiamondDiademPower") == null` 防未来撞 ID。只有“新效果版”才创建 patcher 注册恢复组补丁；default 107 上整个 mod 为零补丁 no-op。此判定只用 typeof/AccessTools 反射，不触 ModelDb/LocManager，避开加载时序坑。
D4. 全部 vanilla 行为改动用 Harmony 补丁完成（不继承 DiamondDiadem、不改原类源）：短路 111 新触发钩子、摘除格挡悬停提示、在 RelicModel 基类虚声明处挂 type-check 的 postfix 恢复计数与回合结束判定、Description getter 改读 RE_ 键；半伤害逻辑经 ModifyDamageMultiplicative 五参/六参二选一动态挂载（PatchTarget 精确签名 → 都失配则上报诊断）。
D5. 计数状态存 `ConditionalWeakTable`（运行期持有、不触存档序列化、不占原类字段）。
D6. 文本资产用 mod pck 独立 RE_ 键（relics 表 + powers 表），16 语言中 107 缺失的 zht/ind 以 eng 兜底（飞拳 ADR-003 先例）。
D3. **mod 程序集内新建最小自定义 power**：`RevertDiamondDiademPower : PowerModel` 只 override 两版稳定的 abstract 成员 Type/StackType；依赖官方原生发现链 `ModelDb.AllAbstractModelSubtypes` ⊃ `GetSubtypesInMods`（已实证）；文本走自建键 REVERT_DIAMOND_DIADEM_POWER.*（slug 随类名自动推导，天然自洽）。
D4. **全部 vanilla 行为改动用 Harmony 补丁完成**（不继承 DiamondDiadem、不改原类源）：短路 111 新触发钩子、摘除格挡悬停提示、在基类虚声明处挂 type-check 的 postfix 恢复计数与回合结束判定、Description getter 改读 RE_ 键。
D5. **启用判定用行为级形状判据**（AfterSideTurnStart 是否为 DiamondDiadem 自己的 override + DiamondDiademPower 是否缺失），SemVer 门只作第二保险——语义上覆盖一切“当前宿主是新效果”的版本而不必枚举版本号。
D6. 计数状态存 `ConditionalWeakTable`（运行期持有、不触存档序列化、不占原类字段）。

## 备选方案及放弃原因

| 备选 | 状态与原因 |
|---|---|
| A. 零依赖自写（Harmony-only） | 原为推荐案，经用户拍板**未采纳**。技术上完全可行（调研已实证官方原生发现链），放弃主因：用户更看重 RitsuLib 的工程化收益（带诊断的补丁框架、optional target 一等支持、失败自禁用语义、日志与后续生态一致性）。技术论证保留于 3.DOCS/002-R-BaseLib与RitsuLib调研.md §五 |
| B1 依赖 BaseLib | 弃：定位“新增内容”标准件，本项目核心是修改 vanilla 行为+一个已被官方原生支持的 custom power，增量价值≈0 |
| B2 依赖 RitsuLib | **✅ 已采纳**（见决策 D0~D6） |
| B3 全面继承实现（子类 override 所有行为含减伤）+ 双配置编译发布变体包 | 弃：工作量翻倍、发布结构复杂化；且 variant-pack 为 RitsuLib 自身分发机制，业务 mod 无现成复用面 |
| B4 文本直接覆写官方同键（不用 RE_ 键） | 有与其他 mod 竞争覆写的合并顺序隐患；社区惯例已是独立键（系列先例一致） |
| B5 不建 buff 实体，减伤逻辑直接挂在伤害计算补丁里、用弱表做标记 | 少了 HUD 图标与 tooltip 表现力（107 原行为的核心可见特征），简化幅度不足以补偿 |

## 后果

- 正面：产物形态仍是三件套，多一层 RitsuLib 前置依赖换来诊断化补丁链路；对 108~110 未调查区间具有形态自适应性（行为级判据）；全部关键落点均有先例背书（达弗修改=RitsuLib 实战模板、回调系=补丁惯例模板）。
- 负面/警惕：玩家侧新增前置库依赖（RitsuLib 需 0.5.x 且声明 min_version）；RitsuLib 自身 0.x 高频迭代、实质单人维护是其上游风险（3.DOCS/002-R-BaseLib与RitsuLib调研.md §二）；首次接触 `IPatchMethod`/`RegisterDynamicPatch` 的组合要注意 async 目标形态。后续游戏若大幅重构 Hook 体系则整组补丁需重审（施工计划阶段 2 checklist 是第一道防线）。
- 触发重新评估的条件：a) 官方未来版本恢复了原 `DiamondDiademPower` 类或改回旧效果 → 本 mod 形态判据自动 no-op；b) 若阶段 2 发现广播器不可 patch 或另有未预料的签名族漂移 → 重新评估零依赖变体或 B3。

## 后续记录

- 2026-08-27 实施落地：骨架+全部补丁组编译通过（RitsuLib 0.5.15 NuGet + 工作坊订阅同版本前置），`build.ps1` 三步流水线（dotnet build → godot --headless --import → --export-pack → 拷贝三件套）跑通，产物已入游戏 mods 目录。实施补充决策：
  - RitsuLib 补丁方法约定确认：每个 IPatchMethod 类仅可含一个 Prefix 与一个 Postfix（ApplyPatch 按 "Prefix"/"Postfix"/"Transpiler"/"Finalizer" 名字各取其一）→ ShowCounter 与 DisplayAmount 两个 getter postfix 拆成独立补丁类；
  - 版本差异目标全部用 OptionalMethod(ignoreIfMissing) 精确签名声明（含 ModifyDamageMultiplicative 的 V5/V6 双声明、AfterSideTurnStart/BeforeSideTurnEnd/AfterCardPlayed），配 HostShapeGate 形态门双保险；
  - `{CardThreshold}` 占位符采用三级退路中的“文本硬编码 2”路线（提取脚本统一 replace），规避 DynamicVarSet 构造时序这一最大不确定点；阈值 2 同时写死于 DiademState.Threshold；
  - `PlayerChoiceContext` 实际命名空间为 MegaCrit.Sts2.Core.GameActions.Multiplayer（非 Context）；
  - Godot 导出要求工程目录有 `.sln`，构建前需 `dotnet new sln` 并 add csproj；
  - 游戏实测前的遗留观察项：①自定义 power 的 HUD 小图标走官方 power_atlas 键缺失时的回退表现是否异常；②111 图集中若仍保留旧 DIAMOND_DIADEM_POWER 条目可做 Icon patch 白得原版图形；③回合结束替换链路（ref Task __result）与 PowerCmd.Apply 的运行时行为。

## 后续记录 3（2026-08-28 第二轮验收反馈处置）

用户反馈两点，取证后修正：

1. **buff 永久常驻（应只在施加后的敌方回合生效）**：根因是我复刻 `RevertDiamondDiademPower` 时漏抄了 107 原版的 `AfterSideTurnEnd(side==Enemy) => PowerCmd.Remove(this)` override——power 由此永不消失。已照抄 107 官方实现补上（`PowerCmd.Remove(PowerModel?)` 两版签名一致，107:287 / 111:291）；dll 二进制验证 override 已编入。107 的完整生命周期为：玩家回合结束（出牌≤2）施加 → 敌方回合减伤生效 → **敌方回合结束立即移除**，下回合重新判定。

2. **图标不对**：日志实锤 `No loader found for resource: res://RevertDiamondDiadem/powers/revert_diamond_diadem_power.png`——mod pck 里的原始 png 缺 remap，运行时根本无法加载；且经 pck-tool 检索证实 **111 官方包中头冠 buff 图标资源原封未动**（`images/atlases/power_atlas.sprites/diamond_diadem_power.tres` + `images/powers/diamond_diadem_power.png.import` + imported ctex 三件俱全，Mega Crit 只删了代码没删资源），官方按 slug 推导的路径在 107/111 上原生就能显示正确图标。修正：**撤销上一轮的 PowerSmallIconPatch/PowerBigIconPatch 与自带 png**（文件与 export_presets 条目一并移除，pck 已验证 0 残留），图标完全回归官方原生路径。上一轮"从 pck 提取裁剪"的结论作废——提取的素材本身没错，错在没必要覆盖 + 载入方式不可行。

沉淀到 3.DOCS/003-T-STS2-Modding机制事实速查.md 的两条新事实：
- mod pck 内的原始 png 运行时不可直接 `ResourceLoader.Load`（无 .import remap），mod 图标只有 `res://{id}/mod_image.png` 走引擎专用通道；
- 官方删除内容型代码时通常不清理美术资源，回改造 frequently 可以直接依赖官方残留资源路径。

## 后续记录 4（2026-08-28 第三轮验收反馈处置：图标修正）

- 用户反馈：撤销图标补丁后 buff 图标回落为 missing 占位图。**后续记录 3 第 2 点的结论有误，在此更正**：官方按 slug 推导的图标路径只对原类名 `DiamondDiademPower`（slug=diamond_diadem_power）有效；我们的类名带 Revert 前缀（slug=revert_diamond_diadem_power），路径指向的官方条目不存在，必然占位。
- 最终方案（比上一轮的两版都简单可靠）：恢复两个 getter postfix（`PackedIconPath`/`ResolvedBigIconPath`），但目标改为**官方原类的资源路径**——`res://images/atlases/power_atlas.sprites/diamond_diadem_power.tres`（HUD 小图标，AtlasTexture 含 margin 全保留）与 `res://images/powers/diamond_diadem_power.png`（tooltip 大图）。这两套资源经 pck-tool 实证在 107/111 官方包中均未删除，走官方 remap 加载，mod 无需自带任何图片。
- 三轮图标方案的迭代教训：自带 mod png（无 remap 不可加载）→ 撤补丁依赖官方路径（slug 不匹配必占位）→ **patch 指回官方原类资源路径**（正确解）。dll 已按 UTF-16 字面量验证两个路径常量编入。
